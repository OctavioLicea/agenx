## Decisiones tomadas

- Antes de comitear cualquier cosa: escaneo completo de diffs y
  archivos nuevos sin trackear (componentes, hooks, features,
  `bovedaPin.js`, assets, docs). Se verificó especialmente
  `bovedaPin.js` contra las bitácoras del 13 de julio para confirmar
  que es exactamente lo documentado (candado de PIN local, SHA-256 +
  salt, no seguridad real) y no algo introducido sin registrar.
- Sin secretos hardcodeados en ningún archivo nuevo; `.env` sigue
  correctamente ignorado.
- Se agregó a `.gitignore`: `.tmp.driveupload/`, `.tmp.drivedownload/`,
  `.history-files/`, `*.lnk` — artefactos de sincronización (Google
  Drive / Cowork) que llevaban apareciendo como archivos sin trackear
  sesión tras sesión, sin ser nunca parte real del proyecto.
- Se encontró y limpió un archivo suelto de ese mismo tipo
  (`.tmp.driveupload/40220`) que sí había quedado commiteado por
  accidente en una sesión anterior — se removió en un commit aparte.
- **Bug de plataforma nuevo, distinto al de "copias congeladas" ya
  documentado en Sesión 11**: en este entorno de Cowork, `git` no
  puede limpiar sus propios archivos de lock (`index.lock`,
  `HEAD.lock`) ni objetos temporales (`.git/objects/*/tmp_obj_*`) —
  cada operación de `git` los deja huérfanos con
  "Operation not permitted" al intentar `unlink`. Workaround que sí
  funcionó: `mv` (rename) dentro del mismo filesystem antes de repetir
  el comando de git — el rename no está bloqueado, solo el
  unlink/delete directo. Los commits en sí se completaron bien (el
  contenido no se corrompió), solo quedó basura inerte de archivos
  `.old*` dentro de `.git/` que no afecta al repo y que el propio Okta
  puede limpiar cuando quiera con acceso de administrador a esa
  carpeta. **Actualización**: además del bug de lock, se detectó un
  segundo bug de sincronización — el archivo real (visible para Okta)
  a veces no coincide con lo que este mismo shell lee momentos después
  (ni `wc -l` ni `git diff` lo detectan como cambiado aunque sí cambió).
  Workaround que funcionó de forma confiable: escribir el contenido
  final directamente desde el shell (no editar por fuera y esperar a
  que se refleje) antes de cualquier `git add`/`commit`.
- El deploy real (`npm run deploy`, que hace `git push` implícito a la
  rama `gh-pages`) no se pudo correr desde Cowork por falta de
  credenciales de GitHub en el sandbox — se dejó todo commiteado y
  Okta corrió el comando desde su propia máquina.
- **Incidente: primer deploy rompió el dominio custom**. Tras correr
  `npm run deploy`, `tuasesor.eventosytech.com` empezó a dar
  "404 — There isn't a GitHub Pages site here". Causa raíz encontrada
  comparando `dist/` contra el `CNAME` de la raíz del proyecto: el
  archivo `CNAME` vivía solo en la raíz, no en `public/`, y Vite solo
  copia el contenido de `public/` al build — cada `npm run deploy`
  publica `dist/` completo a la rama `gh-pages`, así que este deploy
  (el primero corrido en varias sesiones) reemplazó la rama sin el
  `CNAME`, y GitHub Pages deshabilitó el dominio custom. Confirmado
  con `git ls-tree -r origin/gh-pages` (sin `CNAME`) antes del fix.
- **Fix**: se copió `CNAME` a `public/CNAME` para que Vite lo incluya
  en todo build futuro, se commiteó, y Okta corrió `npm run deploy`
  otra vez. Confirmado después vía `git fetch` + `git show
  origin/gh-pages:CNAME` que la rama ya trae el archivo correcto.
- **Verificado en Settings → Pages del repo** (captura de Okta): el
  campo "Custom domain" muestra el dominio correcto (el ".cor" que se
  veía en la captura era el cuadro de texto recortando la "m" final,
  no un typo real) y "DNS check successful" en verde, "Enforce HTTPS"
  activo. La configuración de GitHub está bien.
- **Sitio seguía sin responder al cierre de la sesión** pese a la
  config correcta — tanto `tuasesor.eventosytech.com` como la liga
  default `octaviolicea.github.io/TuAsesor/` devolvían vacío/404 desde
  las herramientas de Cowork. Hipótesis más probable: GitHub
  re-emitiendo el certificado HTTPS y/o caché de su CDN (Fastly) tras
  el cambio de estado del dominio custom — esto puede tardar de
  minutos a un rato. Se descartó que sea un workflow de GitHub Actions
  custom (no existe carpeta `.github/` en el repo, ni en `main` ni en
  `gh-pages`) — el mensaje "pages build and deployment workflow" que
  se ve en Settings → Pages es solo la etiqueta genérica que usa
  GitHub hoy en día, no indica una fuente de deploy distinta.
